# บทบาท
คุณเป็น Business Analyst และ Solution Architect ที่มีประสบการณ์ออกแบบระบบสารสนเทศให้มหาวิทยาลัยในไทย
เข้าใจงานบริหารงานวิจัย ระเบียบการเงินภาครัฐ และการปรับปรุงกระบวนการ (Process Improvement / Lean)

# บริบท
- องค์กร: มหาวิทยาลัย ระบบใช้ในระดับภาพรวมของมหาวิทยาลัย (กองบริหารงานวิจัย) ดูแลทุนทั้งภายในและภายนอก
- สถานะปัจจุบัน: ทำงานด้วยกระดาษและอีเมลเป็นหลัก ยังไม่มีระบบกลาง
- ปัญหาที่คาดว่ามี: เอกสารตกหล่น ติดตามสถานะยาก ส่งเอกสารไปกลับหลายรอบ ข้อมูลกระจัดกระจาย
  และผู้บริหารไม่มีภาพรวมแบบ real-time
- ผู้เกี่ยวข้อง: นักวิจัย/หัวหน้าโครงการ, เจ้าหน้าที่กองวิจัย, เจ้าหน้าที่การเงิน/พัสดุ,
  ผู้บังคับบัญชาที่ลงนามอนุมัติ, ผู้บริหาร

# โจทย์
ออกแบบ "ระบบบริหารจัดการเงินทุนวิจัย" (Research Management System: RMS)
ครอบคลุมช่วงหลังได้รับอนุมัติทุนแล้ว ได้แก่
1. การทำสัญญารับทุน
2. การแบ่งงวดเงินและการเบิกจ่าย
3. การติดตามความก้าวหน้า (รายงานรายงวด, ผลผลิต/ผลลัพธ์)
4. การปิดโครงการ (รายงานฉบับสมบูรณ์, คืนเงินเหลือจ่าย, ปิดบัญชี)

ช่วงก่อนหน้านั้น (ประกาศทุน ยื่นข้อเสนอ พิจารณาข้อเสนอ) อยู่นอกขอบเขต
ให้ถือว่าได้รับข้อมูลโครงการที่อนุมัติแล้วเข้ามาเป็น input

# สิ่งที่ต้องส่งมอบ (เรียงตามลำดับ)

## 1. กระบวนการ As-is
- สรุปขั้นตอนปัจจุบันที่มักพบในมหาวิทยาลัยไทยที่ทำงานด้วยกระดาษ/อีเมล แยกตามช่วงทั้ง 4
- ระบุผู้รับผิดชอบ เอกสารที่ใช้ และจุดที่เป็นคอขวด/ความเสี่ยงของแต่ละขั้นตอน
- ทำเป็น diagram (Mermaid swimlane/flowchart)
- ข้อใดเป็นการสันนิษฐาน ให้ระบุไว้ชัดเจนเพื่อให้ผู้ใช้ยืนยันหรือแก้ไขภายหลัง

## 2. วิเคราะห์และปรับกระบวนการ (To-be)
- แสดงตารางวิเคราะห์ทุกขั้นตอนเดิม: คงไว้ / รวม / ทำอัตโนมัติ / ตัดทิ้ง พร้อมเหตุผล
- ไม่ตัดขั้นตอนที่ระเบียบบังคับ (เช่น ระเบียบการเงินภาครัฐ, เงื่อนไขของแหล่งทุนภายนอก,
  การตรวจสอบภายใน) แต่ให้เสนอวิธีทำให้เร็วขึ้นแทน เช่น digital form, e-signature,
  ตรวจสอบเงื่อนไขอัตโนมัติ
- แสดง diagram To-be และประมาณการว่าจำนวนขั้นตอนและระยะเวลาลดลงเท่าไร

## 3. เอกสาร Requirement
- แยกตามบทบาทผู้ใช้ในรูป User Stories พร้อม Acceptance Criteria หลัก
- Functional requirements จัดกลุ่มตามโมดูล
- Non-functional requirements: ความปลอดภัย, PDPA, audit trail, สิทธิ์การเข้าถึง (RBAC),
  ความพร้อมใช้งาน
- จัดลำดับความสำคัญแบบ MoSCoW และระบุว่าอะไรอยู่ใน MVP

## 4. สถาปัตยกรรมและเทคนิค
- ภาพรวมสถาปัตยกรรมระบบ (diagram)
- Data model หลัก (ER diagram): โครงการ, สัญญา, งวดเงิน, รายการเบิกจ่าย, รายงาน, ผลผลิต, ผู้ใช้/บทบาท
- Workflow/state machine ของสัญญา การเบิกจ่าย และรายงาน
- การเชื่อมต่อระบบที่อาจต้องมี: ระบบการเงิน/ERP ของมหาวิทยาลัย, ระบบ HR, SSO,
  NRIIS ของแหล่งทุนภายนอก (ระบุเป็นทางเลือก)
- เสนอ tech stack 1–2 ทางเลือก พร้อมข้อดีข้อเสีย เหมาะกับทีม IT ขนาดเล็กของมหาวิทยาลัย
- Dashboard/รายงานสำหรับผู้บริหาร

## 5. Prototype
- สร้างต้นแบบที่คลิกใช้งานได้ ครอบคลุม flow หลักของ MVP อย่างน้อย:
  สร้างสัญญา → ส่งคำขอเบิกงวด → อนุมัติ → ส่งรายงานความก้าวหน้า → ปิดโครงการ
- ใช้ข้อมูลตัวอย่าง (mock data) ไม่ต้องมี backend จริง
- เก็บไว้ใน repository นี้ (branch `rms-prototype`) ในโฟลเดอร์ที่จัดไว้ชัดเจน
  พร้อม README อธิบายวิธีรัน

# ข้อกำหนด
- เขียนเป็นภาษาไทย ศัพท์เทคนิคใช้ภาษาอังกฤษได้
- แยกให้ชัดว่าข้อใดเป็นข้อเท็จจริง ข้อใดเป็นข้อสันนิษฐาน
- หลังทำข้อ 1 เสร็จ ให้หยุดเพื่อให้ผู้ใช้ยืนยันกระบวนการ As-is ก่อนทำข้อต่อไป
- จบด้วยรายการคำถามค้างที่ต้องยืนยันกับผู้ใช้งานจริง (เช่น ระเบียบเฉพาะของมหาวิทยาลัย, ระบบที่มีอยู่)
